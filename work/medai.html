02 · Hardware and cloud

MedAI Cabinet

A reminder app cannot open a drawer. Firmware does not know an expiry date. This system puts those two jobs on opposite sides of one API.

Field Hardware and cloud
Role Designed and wrote the web app, backend, firmware, and setup scripts
When May 2026
Stack React, FastAPI, DynamoDB, S3, AWS IoT Core, Bedrock, SNS, ESP32, MQTT/TLS
Code github.com/daonguyenhp/medai-cabinet

Context

Older adults miss a dose, or open the wrong compartment. A carer only sees it if there is a schedule and a way to be notified. A “smart” cabinet easily becomes an app that never touches the object, or a servo circuit with no medication record.

Approach

The React app is for the household: medications, stock, expiry, today’s schedule, doses taken. FastAPI sits in the middle. Records live in DynamoDB, images in S3. An open-drawer command goes through AWS IoT Core over MQTT/TLS to the ESP32. Carer alerts go through SNS.

The symptom conversation calls Amazon Bedrock, using Claude. It is a follow-up layer, not a diagnosis. The ESP32 DevKit firmware drives three SG90 servos, a DHT22 for temperature and humidity, an SSD1306 OLED, an LED, and a buzzer.

What is true

The repo has the four layers: frontend, backend, PlatformIO firmware, and a script that creates the AWS resources. The API covers medications, schedules, dose history, symptom analysis, chat, a dashboard summary, alerts, and device telemetry.

The cloud path needs an AWS account. Bedrock is billed per token. There is no household count, and no clinical accuracy to publish. This triage does not replace a clinician.

If I continue

  1. A local mode with no AWS, so someone can click a schedule and a simulated drawer.
  2. A hard limit on what the symptom layer is allowed to say, with a log of refusals.
