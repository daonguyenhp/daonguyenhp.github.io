OmniTrace

A debugger for multi-agent systems needs the reasoning thread, the checkpoint, and the super-step. Knowing that a request was slow is not enough.

Field Agent systems
Role Writing the telemetry layer
When In progress · version 0.1
Stack Python 3.11+, pytest, ClickHouse, OpenTelemetry GenAI conventions
Code Not on GitHub yet. Layer 1 has spans, semantics, and a ClickHouse sink. No interface yet.

Context

Celesnity shows that one loop can record events and isolate tools. OmniTrace asks the next question: when several agents interleave, how do you separate a meaningful step from network noise, then store it so you can later ask which checkpoint held a decision.

Approach

The tracer keeps the current span in a context variable, so a child span inherits the parent trace and parent id. Each span is one of: chat, text completion, invoke agent, create agent, or execute tool.

Three OmniTrace fields travel with the span and are inherited unless overridden: thread id, checkpoint id, and super-step. A semantic flag marks events that belong to the reasoning trace, apart from network I/O. Prompts and completions are stored only when RECORD_PROMPT is on.

ClickHouse stores a MergeTree table ordered by trace id and start time. The three spatiotemporal fields become columns. Remaining attributes and events stay as JSON strings.

What is true

Tests cover settings, semantics, spans, the tracer, LLM recording, the spatiotemporal fields, and the ClickHouse sink. There is no debug screen. It has not traced a live agent system outside the tests. The repo is not public.

This is the recording layer, not a finished causal debugger. The “why A caused B” part is not written yet.

If I continue

  1. Attach this tracer to the Celesnity loop, in place of the console exporter.
  2. One readable query: for a checkpoint, list the tools that ran and their parent spans.
  3. Redact prompt content before it lands in ClickHouse.
